# 3.4 - Apply, Verify và Archive

**Thời lượng:** 45 phút · **Kết quả:** wishlist chạy được, verify không còn CRITICAL, spec được archive.

## Bước 1 - `/opsx:apply` (20')

```text
/opsx:apply add-wishlist
```

Agent lấy `openspec instructions apply` (gồm tasks, file context, project context), làm **từng task**,
đánh dấu `- [x]` trong `tasks.md` khi xong. Nó sẽ dừng lại hỏi nếu gặp điểm mơ hồ, vấn đề thiết kế
hoặc việc nằm ngoài phạm vi.

Trong lúc chờ, theo dõi tiến độ ở terminal khác:

```bash
openspec status --change add-wishlist
git diff --stat
```

Nếu muốn làm từng phần để review: `/opsx:apply add-wishlist chỉ làm nhóm task 1 và 2`.

## Bước 3 - `/opsx:verify` (10')

```text
/opsx:verify add-wishlist
```

Verify đối chiếu **code thật** với artifact theo 3 chiều:

| Chiều            | Kiểm tra                                                    | Mức độ khi thiếu     |
| ---------------- | ----------------------------------------------------------- | -------------------- |
| **Completeness** | Task đã xong hết chưa; mỗi requirement có code tương ứng    | CRITICAL             |
| **Correctness**  | Code làm đúng requirement; mỗi scenario có test             | WARNING              |
| **Coherence**    | Code theo đúng quyết định trong design và pattern của dự án | WARNING / SUGGESTION |

Báo cáo có bảng tổng hợp và danh sách vấn đề kèm `file.ts:dòng`. Xử lý:

1. Sửa mọi **CRITICAL** (thường do task chưa xong hoặc requirement chưa có code).
2. Với **WARNING** "scenario chưa có test" → yêu cầu agent viết test cho scenario đó.
3. **SUGGESTION**: cân nhắc, có thể bỏ qua kèm lý do.
4. Chạy lại `/opsx:verify add-wishlist` tới khi sạch CRITICAL.

> 💡 Verify chỉ mang tính tư vấn - không chặn archive. Kỷ luật là của team: quy ước "không archive khi
> còn CRITICAL".

## Bước 4 - Archive (5')

```text
/opsx:archive add-wishlist
```

(hoặc bằng CLI: `openspec archive add-wishlist`). OpenSpec sẽ:

1. Kiểm tra artifact và task (cảnh báo nếu còn task chưa xong).
2. Gộp delta vào spec chính: tạo `openspec/specs/wishlist/spec.md`.
3. Chuyển change vào `openspec/changes/archive/YYYY-MM-DD-add-wishlist/`.

```bash
openspec list --specs
openspec show wishlist --type spec
git add -A
git commit -m "feat(wishlist): add wishlist with heart toggle, header badge and /wishlist page"
```

✅ **Checkpoint:** 9 kịch bản thủ công đúng; verify không còn CRITICAL; `openspec/specs/wishlist/spec.md`
tồn tại; `npm run check` pass.

## Tổng kết - So sánh Spec Kit và OpenSpec

Điền bảng (nộp cùng bài):

| Tiêu chí                                         | Spec Kit (coupon) | OpenSpec (wishlist) |
| ------------------------------------------------ | ----------------- | ------------------- |
| Số lệnh / bước đã chạy                           |                   |                     |
| Số file tài liệu sinh ra                         |                   |                     |
| Thời gian từ brief tới code chạy được            |                   |                     |
| Phát hiện được vấn đề trước khi code? Vấn đề gì? |                   |                     |
| Độ khớp giữa code và spec cuối cùng              |                   |                     |
| Phù hợp nhất cho loại việc nào?                  |                   |                     |

Gợi ý thảo luận:

- Spec Kit có **constitution** và **analyze** làm cổng kiểm soát chất lượng mạnh; OpenSpec có **spec
  sống** (`openspec/specs/`) luôn phản ánh hệ thống hiện tại sau mỗi lần archive.
- Sau 10 tính năng, với mỗi công cụ, làm sao một thành viên mới biết hành vi hiện tại của giỏ hàng?
- Có thể kết hợp không? (ví dụ: constitution của Spec Kit + delta spec của OpenSpec)
