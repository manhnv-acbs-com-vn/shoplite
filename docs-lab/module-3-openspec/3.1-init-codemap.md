# 3.1 - Khởi tạo OpenSpec và dùng lại CLAUDE.md làm codemap

**Thời lượng:** 25 phút · **Kết quả:** OpenSpec cài vào ShopLite, `openspec/config.yaml` có project context + codemap.

## Lý thuyết nhanh: OpenSpec khác Spec Kit ở đâu?

|                     | Spec Kit (Module 2)                  | OpenSpec (Module 3)                                                                |
| ------------------- | ------------------------------------ | ---------------------------------------------------------------------------------- |
| Đơn vị làm việc     | Feature (`specs/001-.../`)           | **Change** (`openspec/changes/<tên>/`)                                             |
| Spec sống ở đâu     | Mỗi feature một spec riêng           | `openspec/specs/<capability>/spec.md` - **nguồn sự thật hiện tại** của cả hệ thống |
| Cách mô tả thay đổi | Viết spec mới                        | Viết **delta**: `ADDED` / `MODIFIED` / `REMOVED` requirements                      |
| Kết thúc            | Code xong                            | `archive`: gộp delta vào spec chính → spec luôn phản ánh hệ thống thật             |
| Thế mạnh            | Tính năng mới từ đầu, quy trình chặt | Hệ thống đang chạy (brownfield), thay đổi nhỏ - vừa liên tục                       |

Workflow OPSX (OpenSpec 1.x):

```text
/opsx:explore  →  /opsx:propose  →  /opsx:apply  →  /opsx:verify  →  /opsx:archive
 suy nghĩ cùng      proposal + specs     code theo        đối chiếu         gộp delta vào
 agent (không code)  + design + tasks     tasks.md         code ↔ artifact   openspec/specs/
```

> ⚠️ Tutorial cũ dùng `/openspec:proposal`, `openspec/project.md`, và khối `<!-- OPENSPEC:START -->` trong
> `AGENTS.md`. Các thứ này đã bị bỏ từ OpenSpec 1.0.

## Bước 1 - Tạo nhánh và khởi tạo (7')

Module 3 tách từ `main` (đã có `CLAUDE.md`, `AGENTS.md`, hooks của Module 1), **không** từ nhánh Spec Kit.

```bash
cd shoplite
git checkout main
git checkout -b lab3-openspec
openspec --version                     # >= 1.14
openspec init --tools claude
```

Kết quả:

```text
openspec/
├── config.yaml              # project context + rules (bước 3)
├── specs/                   # spec chính của hệ thống (đang trống)
└── changes/archive/         # change đã hoàn tất
.claude/commands/opsx/       # /opsx:propose, /opsx:explore, /opsx:apply, /opsx:sync, /opsx:archive, /opsx:update
.claude/skills/openspec-*/   # cùng các workflow ở dạng skill
```

> 💡 OpenSpec 1.x **không** đọc, không sửa `CLAUDE.md`/`AGENTS.md`. Nhưng Claude Code luôn nạp
> `CLAUDE.md` vào phiên làm việc, nên các lệnh `/opsx:*` vẫn "biết" nội dung của nó.

## Bước 2 - Bật thêm workflow `verify` (5')

Profile mặc định (`core`) chưa có `/opsx:verify`, cần cho bài 3.4.

```bash
openspec config profile            # chọn thêm workflow "verify" (có thể chọn cả new, continue, ff, onboard)
openspec update                    # sinh lại lệnh cho dự án
ls .claude/commands/opsx           # phải có verify.md
```

Cách không tương tác (macOS/Linux/Git Bash):

```bash
openspec config set profile custom
openspec config set workflows '["propose","explore","apply","update","sync","archive","verify"]'
openspec update
```

> ⚠️ Profile là cấu hình **toàn cục trên máy** (`openspec config path` để xem file), không theo dự án.
> Nếu đồng đội có profile `core` và chạy `openspec update`, lệnh verify trong repo sẽ bị xóa.

Khởi động lại Claude Code để nạp lệnh mới.

## Bước 3 - Dùng lại CLAUDE.md làm codemap cho OpenSpec (10')

`openspec/config.yaml` có trường `context` được OpenSpec **chèn vào mọi artifact** (proposal, specs,
design, tasks) và khi apply. Đây là nơi đặt "bản đồ code" để artifact luôn trỏ đúng file. Ta không viết
lại từ đầu mà **rút gọn từ `AGENTS.md`** (đã có mục Codemap ở Module 1).

Nguyên tắc: `context` chỉ chứa **ràng buộc + codemap rút gọn + con trỏ** tới `AGENTS.md`; không chép
toàn bộ (giới hạn ~50KB và tránh hai nơi lệch nhau).

**Prompt**

```text
Đọc AGENTS.md (mục Tổng quan, Codemap, Quy ước, Quy tắc nghiệp vụ, Definition of Done) và cập nhật
openspec/config.yaml:
- context: (1) yêu cầu viết artifact bằng tiếng Việt nhưng giữ tiêu đề cấu trúc OpenSpec và SHALL/MUST
  bằng tiếng Anh; (2) stack 2 dòng; (3) codemap rút gọn dạng "capability -> thư mục -> file chính" cho
  catalog, cart, checkout, orders, layout; (4) 5 ràng buộc quan trọng nhất; (5) một dòng trỏ tới AGENTS.md
  để xem chi tiết. Tối đa 35 dòng.
- rules: proposal luôn có mục Ngoài phạm vi; mỗi requirement có scenario cho trường hợp lỗi/biên;
  design liệt kê file tạo mới/sửa theo codemap; tasks: mỗi nhóm kết thúc bằng task test, task cuối là npm run check.
Giữ nguyên dòng "schema: spec-driven". Không sửa file nào khác.
```

Kiểm chứng context thật sự được chèn vào instructions của OpenSpec:

```bash
openspec new change thu-context
openspec instructions proposal --change thu-context    # tìm khối <project_context> và <rules>
rm -rf openspec/changes/thu-context
```

So sánh với [reference/config.yaml](reference/config.yaml).

> ⚠️ Viết requirement bằng tiếng Việt kiểu "Hệ thống PHẢI..." sẽ bị `openspec validate --strict` cảnh
> báo vì không có từ khóa SHALL/MUST. Vì vậy context yêu cầu giữ SHALL/MUST bằng tiếng Anh.

## Bước 4 - Commit (3')

## Mở rộng (tùy chọn) - Baseline spec cho hệ thống đang có

Thư mục `openspec/specs/` đang trống, nên mọi change đều là `ADDED`. Với brownfield, có thể "chụp" hành vi
hiện tại thành spec bằng chính quy trình OpenSpec: tạo một change chỉ mô tả, rồi archive.

```text
/opsx:propose baseline-cart: Ghi lại thành spec hành vi HIỆN CÓ của giỏ hàng (không thay đổi code):
thêm/cộng dồn, giới hạn 10 sản phẩm mỗi loại và theo tồn kho, sản phẩm hết hàng, lưu localStorage, đồng bộ tab,
gợi ý miễn phí giao hàng. Đọc src/features/cart và test hiện có để viết requirement chính xác.
Tasks chỉ gồm việc đối chiếu requirement với test hiện có.
```

Sau đó `openspec validate baseline-cart --strict` → `openspec archive baseline-cart -y` →
xem `openspec/specs/cart/spec.md`. Từ giờ, change nào đụng giỏ hàng sẽ dùng delta `MODIFIED`.
